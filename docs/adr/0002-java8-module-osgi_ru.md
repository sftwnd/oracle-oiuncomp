# 0002. Java 8, модуль Java 9+ и OSGi-бандл в одном JAR

[English version](0002-java8-module-osgi.md)

## Контекст

Файлы, сжатые Oracle Installer, встречаются рядом со старыми системами, поэтому библиотека должна работать на
Java 8. Её же подключают модульные приложения Java 9+ и OSGi-контейнеры. Нужен один артефакт, который:

- загружается Java 8 и инструментами того времени;
- на Java 9+ является именованным модулем, который экспортирует только API;
- является OSGi-бандлом с корректными заголовками;
- запускается как утилита командной строки.

## Решение

- Основной код компилируется для Java 8: на JDK 9+ с `--release 8` (профиль `release-8-on-jdk9+`), на JDK 8 — с
  `-source`/`-target 1.8`.
- Дескриптор модуля лежит в `src/main/java9/module-info.java`. На JDK 9+ отдельное выполнение компилятора собирает
  его с `--release 9` в `META-INF/versions/9`, а JAR помечен `Multi-Release: true`. Модуль
  `com.github.sftwnd.oracle.oiuncomp` экспортирует одноимённый пакет.
- Заголовки OSGi вычисляет `bnd-maven-plugin` 6.4.0 и пишет в `target/bnd/MANIFEST.MF`, а `maven-jar-plugin`
  берёт этот манифест. Задаются имя бандла, лицензия, экспорт пакета с версией бандла, `Multi-Release`,
  `Automatic-Module-Name` и `Main-Class`. Импорты и требование `osgi.ee` (JavaSE 1.8) bnd выводит из байт-кода.
- Сборка воспроизводима: время записей JAR задаёт `project.build.outputTimestamp`, а снапшоты получают
  квалификатор `SNAPSHOT` вместо метки времени (`-snapshot`).
- `PackagingIT` проверяет собранный JAR: заголовки бандла, расположение дескриптора, запуск через `-jar` и на
  Java 9+ — описание модуля и запуск утилиты с module path.

## Обоснование

- Java 8 не читает `META-INF/versions`, поэтому дескриптор ей не мешает. Дескриптор в корне JAR сломал бы
  инструменты Java 8, которые разбирают все классы архива.
- `--release 8` проверяет использование API Java 8; `-source`/`-target` сами этого не делают.
- bnd 7 требует Java 17 для запуска, bnd 6.4.0 работает и на JDK 8, поэтому сборка возможна на любом JDK от 8.
  bnd 6 не знает multi-release JAR и предупреждает о классе в чужом каталоге; это сообщение отключено
  (`-fixupmessages`).
- Манифест вынесен из `target/classes`: `Automatic-Module-Name` в нём заставил бы javac при инкрементальной сборке
  принять `target/classes` за модуль при компиляции `module-info.java`.
- `Automatic-Module-Name` совпадает с именем модуля и нужен инструментам, которые не читают `META-INF/versions`.
- Пакет один, реализация в нём закрыта модификаторами доступа, поэтому экспорт пакета не раскрывает внутренние
  классы ни в модуле, ни в бандле.

## Альтернативы

- **Дескриптор модуля в корне JAR.** Проще в сборке, но инструменты Java 8 получают класс версии 53.
- **Только `Automatic-Module-Name`.** Даёт имя модуля, но не ограничивает экспорт: автоматический модуль
  открывает все пакеты.
- **`maven-bundle-plugin` (Felix).** Обёртка над bnd с отдельной упаковкой; `bnd-maven-plugin` встраивается в
  обычную упаковку `jar` без лишних настроек.
- **Отдельные артефакты для Java 8 и Java 9+.** Удваивает публикацию и выбор зависимости у пользователя.
- **Минимальная версия Java 9 или 11.** Противоречит требованию работы на Java 8.

## Последствия

- JAR, собранный на JDK 8, не содержит дескриптора модуля; полный JAR собирается на JDK 9+.
- Новые публичные пакеты нужно добавлять и в `module-info.java`, и в `Export-Package` инструкций bnd.
- Код библиотеки и тесты ограничены API Java 8.
- Модульные проверки `PackagingIT` пропускаются при сборке на JDK 8.
